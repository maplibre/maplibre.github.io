Welcome to the October 2026 edition of the MapLibre newsletter!

Plus, the Style Spec approved new additions, MapLibre Flutter was presented at FlutterCon Berlin, and MapLibre Agent Skills v0.3.0 is out.

A special thanks to our sponsor, Microsoft, for their continued support.

## 📱 MapLibre Native

- We now have stable releases that include the [Plugin API](https://github.com/maplibre/maplibre-native/blob/main/include/mln/plugin/plugin_api.h) announced [last month](https://maplibre.org/news/2026-10-01-maplibre-newsletter-september-2026/). For iOS, we distribute it via Swift Package Manager using a [new distribution repository](https://github.com/maplibre/maplibre-ios-with-plugin-api). For MapLibre Android we also released separate plugin-enabled builds (see the [Artifacts overview](https://maplibre.org/maplibre-native/android/examples/artifacts/) in the docs).
- [MapLibre iOS 7.0.0](https://github.com/maplibre/maplibre-native/releases/tag/ios-v7.0.0) was released. We bumped the minimum iOS version to 15.5. One exciting feature is support for [`global-state`](https://maplibre.org/maplibre-style-spec/expressions/#global-state) expressions. Perhaps less exciting, but very helpful when you need to symbolicate a crash: debug symbols are now included in the XCFramework.
- Pre-releases for MapLibre iOS and MapLibre Android that [support globe projection](https://github.com/maplibre/maplibre-native/releases?q=-globe&expanded=true) were released last month. Please report any issues in [#4533](https://github.com/maplibre/maplibre-native/pull/4533).
- Some large strides by Nikko Vellios, Patrik Drhlik, Andrew Calcutt and others have been made on the [`feature/terrain3d`](https://github.com/maplibre/maplibre-native/pull/4190) branch last month. Stay tuned for pre-releases!

## 🔗 MapLibre Native FFI

MapLibre Native FFI has hit a major milestone; all of its language bindings are now published to their package registries. Kotlin Multiplatform bindings were already on Maven Central, and the C library on GitHub Releases, and now we've also got:

- Dart releases on [pub.dev](https://pub.dev/packages/maplibre_native_ffi)
- C# releases on [NuGet](https://www.nuget.org/packages/Maplibre.NativeFfi)
- Go releases on [pkg.go.dev](https://pkg.go.dev/github.com/maplibre/maplibre-native-ffi/bindings/go)
- Python releases on [PyPI](https://pypi.org/project/maplibre-native-ffi/)
- Rust releases on [crates.io](https://crates.io/crates/maplibre-native-ffi)
- Swift releases on [SPI](https://swiftpackageindex.com/maplibre/maplibre-native-ffi-distribution)
- TypeScript releases on [NPM](https://www.npmjs.com/package/@maplibre/native-ffi) and [OHPM](https://ohpm.openharmony.cn/#/en/detail/@maplibre%2Fnative-ffi-opengl) for the browser, Node, Bun, Deno, Hermes, and ArkTS

[Sargun Vohra](https://github.com/sargunv) also completed internal rework so the library now manages threads that were previously left to the host integration. That change is what made the Flutter integration described in the next section of the newsletter possible. Each language binding is now generated automatically from the C header, which makes it easier to iterate on the API and to maintain or add language bindings.

## 🪶 MapLibre Flutter

### flutter-maplibre

Versions [0.3.7](https://pub.dev/packages/maplibre/changelog#037) and [0.3.7+1](https://pub.dev/packages/maplibre/changelog#0371) for [flutter-maplibre](https://github.com/josxha/flutter-maplibre) were released this month. These are maintenance releases with updated dependencies and a couple of bug fixes.

Work is ongoing for the upcoming `0.4.0` release. The package has been migrated to unified C bindings using [maplibre-native-ffi](https://github.com/maplibre/maplibre-native-ffi), which removed about 160,000 lines of code. Most of that was generated code but it still shows how much complexity the platform-specific SDK bindings added.
The upcoming release also delivers the most upvoted feature request on the issue tracker: better type safety in the API with statically typed layer properties and statically typed expressions.
The prerelease is available on pub.dev now: [v0.4.0-pre.1](https://pub.dev/packages/maplibre/versions/0.4.0-pre.1).

  🎉 [flutter-maplibre-gl 0.28.0](https://pub.dev/packages/maplibre_gl) is
  coming!

The next release closes more than 50 issues since 0.27.0, with one theme: the same call gives the same result on every platform.

- **Typed native bridge:** [Pigeon](https://pub.dev/packages/pigeon)-generated messages replace hand-written method channels on Android and iOS, laying the groundwork for an FFI backend.
- **Consistent error handling and gestures:** shared error codes across platforms, and feature taps, drags and camera events behave the same everywhere.
- **New APIs:** `moveLayer`, `setLayerZoomRange`, `setLayersVisibility`, `panInertia`, image sources on Web, F-Droid-friendly Android builds and more.
- **Updated engines:** MapLibre Native Android 13.7.1, iOS 6.31.0, GL JS 6.14.0.

Most apps upgrade without code changes. See the [migration guide](https://maplibre.org/flutter-maplibre-gl/migration/#upgrading-to-0280) and [docs](https://maplibre.org/flutter-maplibre-gl/) for the exceptions. `maplibre_gl` also passed 150,000 monthly downloads, nearly double August's figure.

## 🤖 MapLibre Agent Skills

MapLibre Agent Skills drops the latest eval-tested MapLibre guidance into agent-assisted coding environments including Cursor, Copilot, Codex and Claude Code so they stop guessing and are kept current beyond their training data.

[v0.3.0](https://github.com/maplibre/maplibre-agent-skills) shipped on 26 October with 11 skills, covering cartography, fonts and glyphs, sprites and icons, terrain, tile sources, PMTiles, source wiring, and Mapbox and v6 migration. It also adds a Claude Code plugin marketplace:

```
/plugin install maplibre-agent-skills --marketplace maplibre/maplibre-agent-skills
```

It's been a big quarter. [Stephanie May](https://github.com/mizmay) overhauled the repo's skill structure and eval process and gave a [well-received](https://nickbearman.com/blog/2026-09-foss4g-2026/index.html) [talk at FOSS4G 2026 in Hiroshima](https://talks.osgeo.org/foss4g-2026/talk/RT8SMH/). [John Carmack](https://github.com/johncarmack1984) hardened the CI and automation and fixed countless small issues along the way.

#### Evals and Automation

- **Drift checks.** A scheduled workflow re-grades the skills, commits dated results, and syncs each skill's `verified` / `provisional` status from the outcome. Since mid-September it has run nearly every week.
- **Release watch.** A weekly job now files an issue when a new MapLibre release removes, renames or deprecates something a skill still mentions.
- **Release automation.** The Changelog is automated from a field in the PR template, and the Release workflow regenerates the table of available skills and their eval status each time a release is cut.
- **AI failure reporting.** Issue and PR templates for AI-failure reports.
- **Spec compliance.** `validate:skills` checks front matter against the Agent Skills spec.

## 🎨 Style Spec

This month we approved:

- [experimental support for `emptyResponse`](https://github.com/maplibre/maplibre-style-spec/pull/1935) to try and support sparse tile matrix by defining better what the server returns as an empty response.
- [support for `elevation` in `fill-extrusion-color`](https://github.com/maplibre/maplibre-style-spec/pull/1851) to better facilitate coloring buildings by height.
- [support for `{fill,line}-layer-blend`](https://github.com/maplibre/maplibre-style-spec/pull/1798) to bring more graphics capabilities to the style spec.

We also included the [TileJSON additions to the docs](https://maplibre.org/maplibre-style-spec/tilejson/), clearly marking which parts come from TileJSON 3.0 and which are MapLibre extensions.

<Announcement>
📝 The MapLibre Style Spec is evolving! Join the discussion on [shadows](https://github.com/maplibre/maplibre-gl-js/discussions/8739), [rooftops](https://github.com/maplibre/maplibre-gl-js/discussions/8734) and immersive 3D, all features we are considering adding to the style spec.

We start with spec changes before implementation so that we can take as much input as possible into account. The best way to move a spec proposal forward is to present it at one of the monthly meetings, so we can shape it together.

</Announcement>
