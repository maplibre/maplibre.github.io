    MapLibre Native

    Cross-platform Plugin System

    An update on the new cross-platform plugin system for MapLibre Native.

    🚀 A first version of the C API has landed this month!

    We also already saw various PRs (#4654, #4692, #4665) that extended the capabilities of the plugin system. This is exactly the approach that we want to take: gradually expand the scope of the plugin system to make sure it fits all the use cases that our users have.

    It should be noted that during this development phase the plugin system is not stable yet. Regular builds also do not include it yet (all integration code is guarded with a MLN_WITH_PLUGINS build flag). However, for those that want to experiment with the plugin API already, we did put out a pre-release for MapLibre Android that includes it. Please see this repository for an example. MapLibre iOS will follow suit.

    Note that these plugins tie directly into the core. The plugins are cross-platform, and thanks to the C API, once the API is stable, people will be able to publish plugins that will continue working across versions. We believe that this has the potential to create a true plugin ecosystem for MapLibre Native. By having a powerful plugin system, we allow people to extend the library and experiment, while keeping the core library stable (and small). Below you can find a small taste of some interesting ideas.

    Call for MapLibre Accessibility Features

    Tim Sylvester implemented the ability to introspect rendered features in #4460 this month. While this functionality was built primarily with testing purposes in mind, it might offer some opportunities for MapLibre Native to better integrate with accessibility tools such as screen readers. We would be very eager to hear from people willing to share their ideas on how to push such accessibility efforts.

    Other news

    • Android can now load PMTiles directly from APK assets, allowing apps to bundle offline tile archives in this format.
    • The semiliteral expression is now supported in Native, matching GL JS. It allows array-valued properties, such as text offsets, to contain elements calculated using expressions.

    🌐 MapLibre GL JS

    💪 We did a large sweep this month over the open issues and closed about 80 of them (~25%). We also swept through the PRs and revived some stale ones. Many thanks to John Carmack for driving this effort!

    Additionally we have added support for the font-faces` style spec property, officially closing one of the last major gaps between native and web.

    We released 8 versions this month: 6.7, 6.8, 6.9, 6.9.1, 6.10, 6.11, 6.11.1 and 6.11.2. These versions are packed with new features, fixes and improvements. Our pace is increasing dramatically with the extensive use of AI, but we make sure to fully review and test all the code that ships in order to keep our quality high. Check out our AI contribution policy in the contributing guide.

    Here are some highlights from these releases, although there are too many to list:

    • The [font-faces](https://maplibre.org/maplibre-gl-js/docs/examples/style-labels-with-font-faces/) style spec property is now supported, which allows using font files with MapLibre. This was one of the last gaps between native and web, and it is now closed.
    • Along with the above addition, we have improved out-of-the-box support for all kinds of complex script languages and made RTL an out-of-the-box feature that doesn’t require an external plugin.
    • The terrain feature is finally production-grade: for a long time terrain performance was lacking, especially on mobile devices, and there were a lot of bugs related to “jumps”. Recent versions have made it smooth and fast.
    • There were some sky-related bug fixes and improvements, so the sky looks a lot better — try it out!
    • A lot of small performance improvements to increase the Lighthouse ranking.

    💙 As always, we would like to thank all the contributors this month, this wouldn’t have been possible without your help!

    🦀 Martin

    Martin 2.0 is now officially in beta! Test it against your setup and check out our new migration guide.

    We released 3 versions this month: 1.16.0, 1.16.1 and the first beta of Martin 2.0 (2.0.0-beta.0). We merged more than 150 non-bot PRs, and Martin 2.0 is now in beta. Please try the beta against your setup and tell us what breaks. We have written a migration guide: 2.0 removes the options that v1.x and v0.x deprecated, changes some defaults and needs PostGIS 3.5 or newer. If Martin 1.16 starts without deprecation warnings for you, you’re probably fine (the only un-warned change is martin-cp -> martin cp).

    Here are some highlights:

    • Tile grids other than Web Mercator: PostgreSQL, MBTiles and PMTiles sources can now be served on other grids, such as national or polar ones. Seven grids from the OGC registry are built in (for example NZTM2000Quad), and you can define your own in the config.
    • Server-side rendering is stable: It is no longer experimental. It has moved out of the default build into the -full Docker images and tarballs due to having some shared library version dependencies.
    • Faster startup: Martin accepts connections while its sources are still loading, and PostgreSQL discovery does less work per table. /health still only reports ready once everything has loaded.
    • Aliases for fonts, sprites and tile sources: give a font fallback stack, a sprite set or a set of tile sources one name, and a style can request it like a single source.
    • CQL2 filters on table sources: write filter: population > 100000 on a table instead of writing a SQL function.
    • A terminal dashboard shows sources, request rates, a live world map of tile requests and the log. In 2.0 it is on by default in an interactive terminal (--no-tui turns it off).
    • martin-cp is now the martin cp subcommand. It can skip now also skip tiles below an empty tile, which took a world copy from 243s down to 11s on our test database.
    • Performance work on the tile cache: on a warm cache, serving a tile’s content dropped from 107µs to 29µs.
    • Unstable (feature-gated) work continued on DuckDB/GeoParquet sources (s3://, hf:// and more, .duckdb files, hot reload) and on remote COG sources.

    As always, we would like to thank all the contributors this month, this wouldn’t have been possible without your help!

    MapLibre Tiles (MLT)

    📦 Announcement: MLT v2 has evolved from a spec skeleton into a fully working format complete with its own high-performance Rust encoder/decoder, docs, and interactive inspector.

    This month was about MLT v2. It went from a header and metadata skeleton to a working format with its own encoder, decoder, docs and inspector. Everything MLTv2 is still behind the unstable-v2 feature while there are still unresolved questions (see below).

    We shipped 13 releases of mlt-core (0.12.7 -> 0.16.0), along with the mlt CLI, the FFI, WASM and Python bindings, and @maplibre/mlt 1.2.1 and 1.3.0.

    Here are some highlights, although there are too many to list:

    • Every column kind now round-trips in v2. That covers strings, floats, nested properties and m-values. Nested properties use an ORC-style node tree, and a nested node’s structure is written once per row instead of once per entry. That saves 13.6% on a group of name* columns and 9.8% on a bag of all properties.
    • Strings. Dictionaries are front-coded, and a layer can share one dictionary across columns. Together that cuts the whole tile by 18.3% on OpenMapTiles and 21.5% on the tiles that one of our sponsors Amazon provided.
    • Floats. A float column can be stored as a dictionary or with ALP, which is chosen only when every value comes back bit for bit. ALP stores a frame of reference, races FastPFOR against varint for its offsets, and packs its two parameters into a single byte. This cuts decimal columns by 19.5% and makes the parameter search about 10x faster.
    • Smaller headers.
      • The extent fits in a nibble.
      • The column and m-value counts share one variant.
      • Raw streams with a fixed element width no longer store their byte length.
      • The spare nibble in the layer header now holds the geometry type when a layer has only one. About 60% of layers are like this and no longer write a types stream.
    • Geometry. Dictionary and tessellated layouts have been merged. A layer made only of tessellated polygons stores can store just its triangles, and triangle indices count from the layer’s first vertex instead of relatively to the start.
    • Presence and dictionary codes. Dictionary children share their parent’s presence bitfield, presence can be run-length encoded again (up to 4% smaller), and dictionary codes are bit-packed when that beats one varint per code.
    • Tile inspector. The new inspector is built on our WASM bindings to the high performance rust encoder/decoder. It shows a hex view of the tile next to a tree of its regions, draws the geometry, loads tiles from a URL, and has filters with live counts. Check it out -> https://maplibre.org/maplibre-tile-spec/inspector/
    • We have also rewritten most of our docs and it should be much more approachable. If something is unclear, that is a bug and we would love your questions.
    • We have also done a bunch of Hardening.
      • Malformed FSST data, oversized dictionary child counts, vertex index overflow and float encodings that don’t fit are now rejected instead of panicking.
      • Polygon rings with no area are skipped during tessellation.
      • Tests moved to cargo-nextest, with a big push on coverage of the error paths in the codecs.
    • Cleanup. We removed the Pseudodecimal encoding, which was never implemented, the Java encoding server, the (currently sadly unmaintained) C++ encoder from CI.

    🎨 MapLibre Compose

    Over the past couple of months, MapLibre Compose has shipped a shared implementation for Android, iOS, and desktop built on MapLibre Native FFI. These releases closed nearly all the previously open issues (about 80!), completed feature parity work for desktop and web, including map styling and proper compositing with Compose UI, added long-requested features including a map snapshotter and imperative styling APIs, plus support and demos for integrating maps with Android Auto and CarPlay.

    StreetComplete, the OpenStreetMap surveying app, has also merged its migration from direct MapLibre Native Android integration to MapLibre Compose, sharing its map implementation across Android and iOS.

    MapLibre Compose is now essentially feature-complete, except for Kotlin Wasm support which is in draft until the next Compose Multiplatform release. The remaining work before 1.0 is improving documentation, performance, finding and squashing bugs, and improving API ergonomics. User feedback is especially important at this stage.
